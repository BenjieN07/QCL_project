1. Executive summary
Build a small, reproducible variational quantum regression experiment that learns two functions with a shared parameterized quantum circuit:
- f_sin(t) = sin(pi*t)
- f_cos(t) = cos(pi*t)
- t is a real input in [-1, 1].
A quantum data-encoding circuit transforms each input into a quantum state. Trainable gate parameters then transform that state. Two measured Pauli-Z expectation values give separate predictions for sine and cosine. Optimize those gate parameters on an ideal local simulator, quantify performance on held-out inputs, compare circuit depths, then evaluate finite-shot effects. If suitable IBM Quantum time remains, deploy frozen, already-trained parameters for a small validation run on physical hardware.

Main research question: How do ansatz depth, initialization, finite sampling, and (optionally) real-device noise affect the accuracy and trainability of a two-output quantum circuit learning model?

Important limitation: Sine and cosine are elementary and can be generated by simple rotations without training. This project is an educational and benchmarking study, not evidence of quantum speedup, quantum advantage, or superior generalization to classical models. Include at least one simple classical baseline and a non-trained direct-rotation reference to be scientifically transparent.

Scope control: Do not attempt VQLS, QAOA, QAPINN, PINO, or full hardware-in-the-loop training in the core seven-day version. These are separate extensions.
2. Scientific specification (agreed starting point)
2.1 Data
- Domain: t in [-1, 1], so the function argument pi*t spans [-pi, pi].
- Training: 48 distinct inputs, with a fixed random seed.
- Test: 24 additional, disjoint inputs, never used for optimization or hyperparameter selection.
- Validation (optional but desirable): Use a separate small holdout for selecting architecture; otherwise label architecture comparisons exploratory and do not use test data to select a final reported model.
- Plotting grid: 101 evenly spaced inputs; use for visualizations, not model selection.
- Keep train/test datasets and seeds fixed across circuit-depth experiments.
2.2 Model
- 2 qubits initially. Reassess only after obtaining a working end-to-end baseline.
- Use a nontrivial, input-dependent feature map inspired by the cited paper, followed by variational rotations and an entangling gate.
- A feasible starting design uses input-derived angles such as arcsin(t) and arccos(t^2) (keep all inputs within the mathematical domain). Exact gate placement is a design decision to document and test.
- Use two observables, Z on qubit 0 and Z on qubit 1. Both outputs are in [-1, 1], consistent with the target range.
- For a useful expressivity comparison, test 1, 2, and 3 trainable layers. Consider re-uploading data at each layer if the shallow circuit underfits. Keep the encoding choice consistent during comparisons.
- Clearly distinguish data-encoding parameters from trainable parameters.
- Avoid a circuit that directly hard-codes sine or cosine into the measured predictions and then treats this as evidence of learning.
2.3 Training
- Use PennyLane's differentiable simulator with the PyTorch interface, and a standard optimizer such as Adam.
- Optimize both functions jointly. Loss per sample is (prediction_sin - target_sin)^2 + (prediction_cos - target_cos)^2; report clearly whether final loss is a sum or average over outputs.
- Start with a modest optimization budget (for example, 200–300 steps) and stop or troubleshoot based on the plotted learning curve rather than claiming guaranteed convergence.
- Save every experiment's seed, depth, step count, optimizer settings, package versions, training history, and best checkpoint.
- Never choose final reported performance using only training loss.
2.4 Evaluation and baselines
Record, separately for sine and cosine:
1. Test MSE and MAE.
2. Maximum absolute test error.
3. Training loss versus step.
4. Actual and predicted curves on train-independent inputs.
5. Model depth, trainable parameter count, gate count, and compiled two-qubit-gate count where relevant.
6. Variance across at least 2–3 initialization seeds if feasible.
Benchmarks:
- Simple classical model: e.g., a small MLP or a modest Fourier-feature regression using the same training/test split. It will likely fit these functions very well; that is useful context.
- No-training reference: a known elementary-rotation construction that directly produces trigonometric expectation values. Label it an analytic reference rather than a learned baseline.
- Quantum depth study: same encoding and optimizer budget with 1, 2, and 3 trainable layers.
2.5 Sampling and hardware validation
- First train and evaluate exact expectation values locally.
- Then perform finite-shot local simulation (suggested counts: 256, 1,024, and 4,096 shots). Measure prediction variability on a fixed set of inputs across repeated draws.
- Only after local validation, consider an IBM Quantum run using frozen trained parameters, approximately 7–9 test inputs, and a conservative shot count chosen after preflight checks.
- Before any real-QPU submission: verify your IBM account's current available Open Plan allowance, active backend, scheduling limits, transpiled circuit depth, qubit layout, and provider/API compatibility. The frequently advertised “10 minutes” is not a promise that any specific experiment will fit.
- Make real hardware an explicit opt-in. Never submit paid/limited QPU jobs automatically, infer credentials, or store tokens in tracked files.
- Hardware comparison: ideal exact vs local finite-shot vs real hardware at the same trained parameters and input locations. Do not call frozen-parameter validation “training on hardware.”

6. Questions to address in the final report
1. Model design: Why this feature map, ansatz, and choice of two readout observables?
2. Trainability: Does loss reliably decrease? How sensitive is the result to random initialization?
3. Generalization: How do held-out errors compare with training errors?
4. Expressivity: Do deeper circuits help enough to justify more trainable parameters and gates?
5. Measurement statistics: How closely do empirical errors follow the expected reduction of shot noise with more shots?
6. Device transfer (if used): How large is the difference between ideal predictions and real-QPU predictions, and what are plausible noise/transpilation explanations?
7. Classical context: Is a classical baseline better or simpler for these elementary functions? State this honestly.
8. Limits: Small problem, limited seeds, narrow test domain, hardware time constraints, no claim of quantum advantage, and no proof of barren plateaus.
